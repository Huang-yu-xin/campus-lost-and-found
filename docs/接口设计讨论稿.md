## 两条业务流程

招领：发布并审核通过 → 他人提交认领申请 → 双方留言核实 → 发布人确认或驳回 → 确认后的线下交接 → 发布人确认完成并归档。

寻物：发布并审核通过 → 他人提交文字线索 → 双方私有留言 → 发布人标记已找回并归档。线索没有批准或物品归属裁决流程，可以同时存在多个提供者。

标记找回不自动修改其他招领信息、创建认领申请或宣布线索提供者持有该物品。

## 联系方式权限决策与补充设计

推荐按“具体认领申请中的对象”授权，而不是设置一个面向所有申请人的全局公开开关。

- 默认隐藏。持有人仅能授权展示自己的资料，双方分别决定，不能替对方授权。
- 已确认：只对已确认认领的另一方开放授权；申请提交后可以留言，但不自动获得联系方式。
- 建议首版仅支持选择展示个人资料中的手机号、邮箱，不另增加微信号字段。
- 建议支持随时撤回；后续查询立即按新权限判断，不能收回对方已经看到的信息。
- 已确认：交接完成后授权失效，停止新的联系方式查询；历史留言保留。
- 建议线索模块暂不提供联系方式授权，仅使用站内留言，避免扩展第一版范围。
- 公共详情、公共列表、申请列表和操作日志不夹带联系方式。只有专用查询接口返回明确获准展示的字段。
- 管理员身份本身不赋予读取所有联系方式的权限。

授权开放阶段及完成后失效已确认。字段、版本控制、资料修改时撤回等补充设计见完整合同 BR-07；线索第一版仅用私有留言。原需求 FR-06 与“页面和接口都不显示联系方式”的表述需要统一为“公共接口不展示；私有接口仅在授权和业务条件同时满足时展示”。

## 留言和线索的补充规则建议

| 情况 | 建议权限 |
| --- | --- |
| 认领待确认、已确认 | 该申请人与发布人可读写 |
| 认领已驳回、已完成 | 双方可查历史，不再发送 |
| 寻物信息仍有效 | 该线索提供者与寻物发布人可读写 |
| 寻物信息已找回或关闭 | 双方可查历史，不再发送 |
| 无关用户、同一物品的其他申请人 | 不可查看这条私有会话 |
| 管理员处理举报 | 仅查看关联举报的会话，并留存访问记录 |

线索建议限制为 10～500 字；同一人对同一寻物信息只创建一条线索，后续通过留言补充。发布人不能给自己提交线索。提交者身份由服务端登录会话获取。

完整合同 BR-04、BR-05 已给出下架和违规处理的状态草案，供团队评审；物品不可用后不能继续确认或交接。

## 受本轮决策影响的接口草案

所有路径包含 /api/v1 前缀。下表保留本轮受影响的接口边界；完整字段、错误、分页和前置条件已补到 0.1.0-draft 合同。

| 方法与路径 | 用途 | 调用者 |
| --- | --- | --- |
| POST /api/v1/items/{itemId}/clues | 提交文字线索 | 已登录且不是发布人的用户；仅限有效寻物信息 |
| GET /api/v1/items/{itemId}/clues | 分页查询收到的线索 | 寻物发布人 |
| GET /api/v1/me/clues | 分页查询自己提供的线索 | 当前用户 |
| GET /api/v1/clues/{clueId} | 查询线索详情 | 该线索双方 |
| GET /api/v1/clues/{clueId}/messages | 分页查询线索留言 | 该线索双方 |
| POST /api/v1/clues/{clueId}/messages | 发送线索留言 | 该线索双方且流程允许发送 |
| POST /api/v1/items/{itemId}/resolve | 标记寻物信息已找回 | 寻物发布人 |
| POST /api/v1/items/{itemId}/claims | 提交认领申请 | 已登录且不是发布人的用户；仅限可认领的招领信息 |
| GET /api/v1/claims/{claimId}/messages | 分页查询认领留言 | 该申请双方 |
| POST /api/v1/claims/{claimId}/messages | 发送认领留言 | 该申请双方，提交后开放 |
| PUT /api/v1/claims/{claimId}/contact-permission | 设置或撤回自己的联系方式授权 | 该申请参与者，申请 CONFIRMED 且物品 PUBLISHED |
| GET /api/v1/claims/{claimId}/counterparty-contact | 获取对方授权展示的联系方式 | 同时满足参与者身份、业务状态和对方授权条件的用户 |

完整合同采用 phoneVisible、emailVisible 和 expectedVersion；两个开关 false 表示撤回。对象由该申请另一方确定，不接受任意 recipientId 或 ownerId。返回当前获准字段，禁用响应缓存；资料改变时撤回对应字段授权。

普通物品详情接口始终不增加手机号、邮箱字段。自己的资料查询仍属于个人中心接口。

## 状态与数据设计建议

- 物品类型区分 LOST 和 FOUND，线索只绑定 LOST，认领只绑定 FOUND。
- 物品审核状态与认领状态分别定义，不复用同一套枚举。
- 寻物标记找回建议使用物品 ARCHIVED 状态及结束原因 FOUND，避免与招领交接完成混淆。
- 线索核心数据记录 id、lostItemId、providerId、content、createdAt。首版不增加 readAt 已读跟踪、relatedFoundItemId 或图片字段。
- 对 lostItemId 与 providerId 建立唯一约束，配合服务端校验避免重复线索。
- 留言组件可以复用；线索与认领必须分别校验所属关系，不允许通过更换对象编号读取其他会话。
- 联系方式授权建议单独记录申请、授权人、允许字段与更新时间，不复制联系方式到公共业务对象。
- 寻物归档与线索提交需要处理并发，确保归档后不能插入新的有效线索。
